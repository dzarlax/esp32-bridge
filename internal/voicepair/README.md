# Voice pairing: local implementation and deployment constraints

The optional integration in `internal/voicepairsetup` connects this package to the admin and device HTTP routes and to the voice WebSocket hub. It is disabled by default. Admin routes require admin authentication and CSRF protection; pairing requests require TLS on the actual Bridge listener. Promotion and revocation are serialized with hub routing changes. A fleet key or device ID alone does not authenticate a device.

The pending token is derived by domain-separated HMAC from the pending master and stored keyed session digest, IDs, and random generation. Compromise of that master and state exposes derivable pending credentials. The distinct integrity key authenticates persisted state; the signing key signs clear commands. Missing or mismatched pending master disables new pairing while active verifiers remain usable. Restart discards sessions and challenges; a fresh physical pairing is required. Key provisioning, backup, rotation and restoration are not implemented here.

**Deleting state or restoring an older, valid backup can restore legacy mode or an already revoked credential.** Restoration must remain offline and fail closed until an operator reconciles every binding against an independent authoritative revocation record or invalidates affected credentials and re-pairs. This package has no rollback-resistant counter and cannot enforce that procedure itself. Do not deploy until an operational rollback-protection procedure is established and independently reviewed.

The staged main Compose enables TLS on the Bridge listener and retains its shared external Docker networks. The separate Traefik ServersTransport verifies the backend CA and SAN. This path passed the isolated system test; it has not been applied or verified in production. Pairing remains disabled by default in the application, and deployment still requires its own gate and verification of the actual backend link. See `deploy/voice-pairing/README.md` for the configuration and rollback procedure.

For a future deployment, `VOICE_PAIRING_ENABLED=true` requires administration, `ADMIN_BASE_URL`, and `VOICE_PAIRING_HTTPS_ORIGIN` matching its canonical HTTPS origin with an explicit port. Set `VOICE_PAIRING_STATE_DIR`, separate `VOICE_PAIRING_MASTER_FILE` and `VOICE_PAIRING_INTEGRITY_FILE` (each exactly 32 bytes), distinct `VOICE_PAIRING_MASTER_ID` and `VOICE_PAIRING_INTEGRITY_ID`, and `VOICE_PAIRING_SIGNING_FILE` containing a P-256 private key. `VOICE_PAIRING_TLS_CERT_FILE` and `VOICE_PAIRING_TLS_KEY_FILE` configure TLS on the Bridge listener itself; the TLS private key must differ from the signing key. Private key files must be regular files with mode 0600, not symlinks or hard-linked to one another. The publisher token remains separate. No keys or production values are provided here.

`VOICE_PAIRING_LEGACY_MIGRATION=true` explicitly permits the configured legacy subscriber and target until the first successful signed ACK. The hub then discards the legacy session and uses only the selected paired target. Revocation or loss of the selected target does not automatically restore legacy routing. With migration disabled, clear the legacy subscriber and target settings before enabling pairing.

State format version 3 records one selected target. ACK promotion selects the newly paired device atomically with its binding, and revocation clears the target when it matches. Other active verifiers remain stored, so the hub must independently enforce `SelectedTarget` on authentication and fanout. Earlier state versions are rejected rather than migrated automatically; this isolated package has no deployed state.

QR format HDV2 binds the request to the device's canonical HTTPS origin using the first 15 bytes of SHA-256(origin). Approval compares that value against the configured Bridge origin in constant time; HDV1 is rejected. The owner must scan the display's code into the authenticated panel on the intended Bridge. The device verifies the HTTPS certificate and hostname and freezes the origin for the session.

The authenticated managed-mode marker is set on the first successful ACK and never automatically cleared by cancellation, revocation, loss of target, or restart. Invalid state fails closed. Missing state is indistinguishable from first startup; protecting against its deletion or rollback requires the external procedure above.

The clear_ack pre-authentication replay cache is in memory, expires entries after 30 seconds and resets on restart. Its security depends on confidentiality of the pre-signature over the verified TLS path; it does not prevent reuse of a leaked pre-signature after expiry or restart.
