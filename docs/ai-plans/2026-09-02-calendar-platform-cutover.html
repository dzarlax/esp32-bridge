Calendar Platform → ESP32 Bridge

Одобрено · реализация готова к production rollout

Задача

Перевести существующий endpoint Bridge GET /api/calendar?date=YYYY-MM-DD с календарей Home Assistant на новый Calendar Platform из calendar-mcp, не меняя контракт, который уже использует HomeDash.

Что работает сейчас

  • Bridge получает список /api/calendars и события каждого календаря через Home Assistant, затем отдаёт компактные поля s, sh, sm, eh, em, ad, ci.
  • Фильтрация календарей сейчас захардкожена и зависит от имён/ID Home Assistant; порядок полученного списка определяет цвет события на дисплее.
  • Calendar Platform уже имеет отдельный read-only native API: GET /api/native/v1/events?start=RFC3339&end=RFC3339&calendar_id=…, Bearer-аутентификацию и HTTPS-маршрут в production Compose. Ответ содержит items с title, calendar_id, start/end.date либо start/end.date_time, а также явный IANA time_zone для событий со временем.

Предлагаемое поведение

  • Bridge использует только native read API Calendar Platform и отдельный его токен; права записи не добавляются.
  • В Bridge появляется явный список разрешённых canonical calendar IDs (CALENDAR_PLATFORM_IDS). Его порядок задаёт стабильный ci; скрытые и рабочие календари не попадут на домашний экран случайно.
  • Если Calendar Platform не настроен, endpoint сохраняет текущий HA-режим. Когда заданы все новые настройки, он читает только новый источник — это позволяет безопасно сравнить ответ до переключения production.
  • События приводятся к локальному дню Europe/Belgrade: учитываются события, пересекающие выбранный день, и all-day события с корректной эксклюзивной датой окончания. Выходной JSON и прошивка не меняются.

Модели и маппинг данных

Внешний контракт HomeDash не меняется. Bridge вводит внутреннюю типизированную модель ответа Calendar Platform и преобразует её в существующий компактный model.CalendarEvent.

Calendar PlatformBridge / HomeDashПравило
items[].titles / SummaryСанитизация для шрифтов ESP32; пустой заголовок становится безопасной подписью.
items[].start.date_timesh, smПарсится как RFC3339; отображается в Europe/Belgrade, а не в timezone хоста Bridge.
items[].end.date_timeeh, emТа же локальная зона; событие, пересекающее полночь, остаётся видимым в каждом затронутом дне.

items[].calendar_idci / CalIdxИндекс равен позиции canonical ID в CALENDAR_PLATFORM_IDS; цвета не зависят от порядка ответа сервиса.
items[].status—Отменённые события не передаются на дисплей.
items[].id, provider, sources, complete—Не нужны прошивке; используются только для диагностики Bridge без выдачи лишних данных на устройство.

Новые настройки Bridge: CALENDAR_PLATFORM_BASE_URL, CALENDAR_PLATFORM_TOKEN, CALENDAR_PLATFORM_IDS и CALENDAR_TIME_ZONE (по умолчанию Europe/Belgrade). Режим Calendar Platform включается только когда задан весь набор; иначе остаётся текущий HA путь.

Предположения и открытый выбор

  • Используем именно calendar-mcp, а не Swift-клиент calendar-app.
  • Нужно определить фактический список календарей для HomeDash. По умолчанию предлагаю перенести только те личные календари, которые раньше не были отфильтрованы Bridge; перед production переключением сверим их canonical IDs через /bootstrap.
  • Для надёжного переключения потребуется наличие CALENDAR_NATIVE_APP_TOKEN в production secrets Calendar Platform и отдельные Bridge-переменные. Значения секретов не попадут в Git или в план.

Вероятные изменения

  • internal/config/config.go — URL, токен, разрешённые IDs и timezone Calendar Platform.
  • internal/handler/handler.go — клиент native API, строгий маппинг событий и выбор источника.
  • internal/handler/handler_test.go и новые fixture-тесты — auth, URL/query, timezone, all-day, multi-day, ошибка одного источника и стабильные цвета.
  • .env.example, README.md — конфигурация и точное описание источника.
  • docs/ai-plans/2026-09-02-calendar-platform-cutover.html — итог реализации, проверки и rollout.
  • Production env/Compose для Calendar Platform и Bridge — только после кода, тестов и отдельной проверки готовности сервисов.

Шаги реализации и rollout

  1. Добавить настройки, валидировать их как единый набор и не логировать токен.
  2. Реализовать native API-клиент с Bearer-токеном и bounded timeout; для каждого configured ID отправлять query-параметр calendar_id.
  3. Сконвертировать типизированный ответ в текущий model.CalendarEvent, санитизировать заголовок, отбрасывать отменённые/некорректные события и сортировать детерминированно.
  4. Покрыть маппинг и fallback HA тестами, прогнать Go tests/vet и сборку образа.
  5. Развернуть Calendar Platform с read-only native токеном и проверить с Bridge-хоста: health, /bootstrap, запрос одного дня без раскрытия токена и состав/время событий.
  6. Добавить конфигурацию Bridge, развернуть только Bridge, сверить его /api/calendar с Calendar Platform на текущую и следующую дату, затем проверить экран «День» на дисплее.

Проверки

  • go test ./... и go vet ./... в Bridge.
  • Существующий JSON-контракт /api/calendar остаётся совместимым с HomeDash.
  • Fixture cases: timed event с offset, событие через полночь, one-day и multi-day all-day, повторяющееся instance, пустой ответ, 401/5xx upstream.
  • Ручная QA: выбранный день, соседний день и экран с несколькими календарями показывают корректные время, порядок и стабильные цвета; не нужно выпускать OTA, потому что контракт прошивки не меняется.

Реализация: 2 сентября 2026

  • В Bridge добавлены CALENDAR_PLATFORM_BASE_URL, CALENDAR_PLATFORM_TOKEN, CALENDAR_PLATFORM_IDS и CALENDAR_TIME_ZONE. Неполная конфигурация отклоняется при запуске.
  • /api/calendar переключается на token-защищённый native API Calendar Platform при полном наборе настроек; иначе сохраняет HA fallback.
  • Добавлены typed decoding, ограничение ответа 1 MiB, allowlist календарей, стабильные цветовые индексы, локальная дата Europe/Belgrade, фильтрация отменённых и некорректных событий.
  • Пройдены go test ./..., go vet ./... и go build ./cmd/server. Тесты покрывают Bearer auth, IDs, all-day, событие через полночь, отмену и некорректные/вне диапазона события.

Риски и откат

  • Неверный canonical ID или токен даст пустой/401 ответ; до cutover это обнаружит authenticated /bootstrap и проверка Bridge endpoint.
  • Неявный часовой пояс и all-day end date могут сдвинуть событие на соседний день; это закрывается conversion tests и сравнением реальных двух дней.
  • Если новый источник недоступен после переключения, убрать новые Bridge-переменные и перезапустить Bridge: endpoint немедленно вернётся к прежнему HA-календарю. Данные календарей и прошивка не изменяются.

Production rollout

Пользователь одобрил реализацию и rollout. Перед переключением Bridge будет подтверждён health Calendar Platform и token-защищённый native API; секреты останутся только в production env. OTA для этой миграции не требуется.
